## Context

JAAR (`helm/jaar/`) wraps the upstream `agentregistry-dev/agentregistry` OSS chart with a bundled Postgres, deployed via its own ArgoCD Application CR and `jaar` namespace, reachable at `jaar.jarvis.io` through a dedicated HTTPRoute. Two things currently depend on it:

1. **Skill distribution**: `worker/entrypoint.sh` (Step 4) starts an unprivileged dockerd, authenticates to GHCR, and runs `arctl skill pull <name> <dir> --version <v> --registry-url $JAAR_URL` per skill reference on the `Worker.skills` JSON column (`{name, version}` objects, see `backend/app/models/worker.py:32`, `backend/app/schemas/worker.py`). The pod only sets `privileged: true` when `skills` is non-empty (`backend/app/services/k8s.py:227`), purely to run dockerd for the OCI pull.
2. **Dashboard visibility**: `frontend/src/api/jaar.ts` + `frontend/src/pages/Dashboard/Dashboard.tsx` call JAAR's HTTP API directly to show per-type artifact counts (MCP Servers, Agents, Skills, Prompts).

`artifacts/skills/<name>/` in this repo holds a `SKILL.md` + `Dockerfile` per skill, built and pushed to GHCR by CI, then registered into JAAR by `arctl` (per `skill-ci-publishing` spec) so `arctl skill pull` can retrieve them by name@version.

Google's Gemini Enterprise Agent Platform (`docs.cloud.google.com/gemini-enterprise-agent-platform`) ships a managed Agent Registry with no concept of "skills" — its data model is agents, MCP servers, and endpoints. Agents get auto-discovered on GKE via a `registry.gke.io/functional-type: "AGENT"` label plus an `a2a-protocol.org/agent-card` annotation pointing at a live A2A Agent Card endpoint (`/.well-known/agent-card.json`), and a pod-level `iam.gke.io/spiffe-identity-type: agent-identity` annotation for Workload Identity. None of the specifics of Fleet/Hub prerequisites, required IAM roles, or whether the API is enabled in the target GCP project are documented publicly — these are resolved empirically during implementation, not assumed here.

## Goals / Non-Goals

**Goals:**
- Remove JAAR (chart, namespace, Postgres, gateway route) entirely.
- Replace OCI-based skill distribution with a GCS-bucket-backed fetch, dropping the privileged/dind requirement for skill-enabled worker pods.
- Register the JARVIS backend and/or MCP server with Gemini Enterprise Agent Registry via GKE auto-discovery (A2A Agent Card).
- Keep the worker's skill-pull flow idempotent (skip if already cached) and resume-safe, matching the existing cached/pulled counters pattern in `entrypoint.sh`.

**Non-Goals:**
- Provisioning the GCS bucket, its IAM bindings, or enabling the Gemini Enterprise Agent Platform API — these are infra/Terraform changes whose owning repo is an open question (see Open Questions), not implemented as part of this change's tasks beyond documenting the requirement.
- Building a general-purpose A2A agent (multi-skill negotiation, agent-to-agent calls) — only the minimal Agent Card endpoint needed for registry auto-discovery.
- Changing how workers execute Claude Code sessions, resume logic, or the terminal bridge — unrelated to skill/registry distribution.

## Decisions

### 1. Skills live in GCS as plain files, not as a "registry" artifact type
**Decision**: `artifacts/skills/<name>/` content (currently `SKILL.md` + a `Dockerfile` used only to build an OCI image for JAAR) is synced as plain files to `gs://<bucket>/<name>/<version>/` by CI/Makefile. The per-skill `Dockerfile` is dropped since there's no OCI image to build anymore.
**Why over alternatives**: Gemini Enterprise Agent Registry has no skills concept, so keeping skills OCI-packaged just to satisfy a registry that can't host them adds no value. GCS is simpler, requires no dind/privileged containers, and versioning via object path (`<name>/<version>/SKILL.md`) is sufficient — no need for a package format.

### 2. Worker fetches skills via `gcloud storage cp`, not the GCS client library
**Decision**: `worker/entrypoint.sh` shells out to `gcloud storage cp -r gs://$SKILLS_BUCKET/<name>/<version> "$skill_dir"` (or `gsutil cp -r` as fallback) instead of adding a Python/Node GCS SDK dependency.
**Why over alternatives**: The worker image is a bash entrypoint calling CLI tools throughout (git, arctl); a CLI call keeps the same style and avoids adding a language runtime dependency just for this fetch. `gcloud`/`gsutil` is already a reasonable base-image addition versus wiring credentials into a custom script.
**Alternative considered**: Signed URLs generated by the backend — rejected because it re-introduces a JAAR-shaped backend dependency (the whole point of GCS is direct, backend-independent worker access via Workload Identity).

### 3. Skill-enabled pods drop `privileged: true` and the dockerd bootstrap entirely
**Decision**: Since GCS fetch needs no docker daemon, `backend/app/services/k8s.py`'s `has_skills` branch that sets `privileged=True` is removed along with `worker/entrypoint.sh`'s dockerd start/stop and GHCR docker-login block.
**Why**: This was the sole reason skill-enabled workers ran privileged (see CLAUDE.md Known Limitations: "Skill-enabled (dind) worker pods still blocked by `deny-privileged-containers`" in the sandbox cluster). Removing it resolves that limitation as a side effect and shrinks the pod's attack surface.

### 4. Worker identifies skills by `{name, version}` against GCS object paths, keeping the existing `Worker.skills` JSON shape
**Decision**: Keep `Worker.skills: list[{name, version}]` unchanged in the model/schema; only the resolution mechanism (`JAAR_URL` + `arctl` → `SKILLS_BUCKET` env var + `gcloud storage cp`) changes.
**Why**: Avoids a migration on the `Worker` table/schema and keeps the frontend's skill-selection UI untouched; only the pod-spec plumbing and worker script change.

### 5. Agent Card endpoint lives on the MCP server, not the backend
**Decision**: Add `/.well-known/agent-card.json` to `artifacts/servers/jarvis` (the MCP server), not `backend/app/main.py`.
**Why over alternatives**: The MCP server is already the artifact-registry-facing surface (it's what JAAR previously cataloged as a "server" artifact) and is the natural analogue of "the agent" from an external-registry point of view; the backend is JARVIS's internal task-management API, not an agent surface. Putting the Agent Card there keeps the backend free of A2A-protocol concerns it doesn't otherwise need.
**Open question**: whether GKE auto-discovery expects the Agent Card on every agent-labeled Deployment or just one — resolved during implementation by testing against whichever GCP project ends up hosting this (see Open Questions).

### 6. Dashboard "Agent Registry" card degrades gracefully instead of blocking on Phase 2
**Decision**: `frontend/src/api/jaar.ts` is replaced with a client that reads the skills count from a lightweight backend endpoint backed by a GCS bucket listing (backend proxies this — the frontend never talks to GCS directly). Agents/MCP Servers/Prompts counts are hidden (or shown as "—") until Gemini Enterprise Agent Registry's read API is confirmed reachable from JARVIS's backend, since no public querying mechanism was found during research for this change.
**Why**: Ships the low-risk half (skills/GCS) without blocking the whole card on Phase 2's unresolved registry-read-API question.

## Risks / Trade-offs

- [GCS bucket / Gemini Enterprise API provisioning lives outside this repo] → Mitigation: tasks.md calls out the exact bucket name/path convention and IAM role (`roles/storage.objectViewer` scoped to the bucket) the worker's Workload Identity needs, so whichever repo owns the Terraform has a concrete contract to implement against; JARVIS-side changes are written to fail loudly (clear error log) if the bucket/env var is missing, rather than silently no-op.
- [A2A Agent Card + GKE auto-discovery prerequisites (Fleet/Hub membership, IAM roles, SPIFFE Workload Identity support) are undocumented publicly] → Mitigation: Phase 2 tasks are scoped to "implement the Agent Card endpoint and labels; verify registration empirically" rather than assuming a specific IAM role set up front; if a genuine blocker turns up (e.g. Autopilot doesn't support the SPIFFE annotation), that's surfaced as a follow-up change rather than silently skipped.
- [Losing JAAR removes the only place Agents/Prompts artifacts were ever actually cataloged, even though `artifacts/agents/` and `artifacts/prompts/` are currently just `.gitkeep` placeholders] → Mitigation: no functional loss today since both directories are empty; Phase 2 registers what does exist (the MCP server) and leaves agents/prompts registration as future work once content exists.
- [`gcloud storage cp` requires the worker image to carry the Google Cloud SDK, growing the image] → Mitigation: acceptable trade-off since it replaces dockerd + `arctl` + GHCR docker-login (net reduction in image complexity/attack surface), not a pure addition.
- [Breaking change for any in-flight stateful workers with skills already pulled via the old JAAR path] → Mitigation: `entrypoint.sh`'s existing cache check (`[ -f "$skill_dir/SKILL.md" ]`) is format-compatible — already-pulled skills on a PVC are left alone; only new pulls use the GCS path.

## Migration Plan

1. Land Phase 1 (GCS skills) behind the new `SKILLS_BUCKET` env var; keep `JAAR_URL`/`arctl` code path removable in the same commit since there's no need to run both simultaneously — this is a hard cutover, not a dual-write period, since skill-enabled workers are ephemeral/stateful pods recreated on demand, not a live migration of running state.
2. Delete `helm/jaar/`, `argocd/jaar-app.yaml` (+ `-local`), `secrets/jaar-secret*.yaml`, and the `jaar` namespace resources in the same change so there's no dangling half-migrated state.
3. Update the dashboard card and CI publishing in lockstep with the worker change (same PR/change), since `skill-ci-publishing`'s job is what populates the bucket the worker now depends on.
4. Land Phase 2 (Agent Card + GKE labels) as a follow-up within the same OpenSpec change but its own task group, since it has independent, higher-uncertainty infra prerequisites — implementation can proceed once Phase 1 is verified working.
5. Rollback: reverting this change's commits restores JAAR/arctl; no data migration is needed either direction since `Worker.skills` shape is unchanged (Decision 4).

## Open Questions

- Which repo owns the GCS bucket + IAM Terraform (this JARVIS repo gaining its own minimal Terraform, or an existing infra repo)? Needs a decision before Phase 1's infra half can be applied — the JARVIS-side code will read `SKILLS_BUCKET` from env/ConfigMap regardless of where the bucket is declared.
- Is the Gemini Enterprise Agent Platform API enabled (or enable-able) in whichever GCP project ends up hosting JARVIS? Blocks Phase 2 entirely until confirmed.
- Does GKE auto-discovery require Fleet/Hub cluster registration, and does the target cluster (Autopilot) support the `iam.gke.io/spiffe-identity-type: agent-identity` Workload Identity mode? Unknown until tested.
- Should `artifacts/agents/` and `artifacts/prompts/` gain real content as part of this change, or stay placeholders until something needs registering? Currently assumed: stay placeholders (out of scope).
