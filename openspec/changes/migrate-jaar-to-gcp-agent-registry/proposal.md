## Why

JAAR (the self-hosted AgentRegistry OSS chart, `helm/jaar/`) requires its own Postgres, namespace, gateway route, and a privileged/dind sidecar in every skill-enabled worker pod just to pull skill files via OCI images — and it isn't even deployed on the target sandbox cluster today (only used for local dev via `make deploy-local`). GCP's managed Agent Registry API (`agentregistry.googleapis.com`) is already enabled on the target project and has a first-class, versioned `Skill`/`SkillRevision` resource whose `Frontmatter` schema is purpose-built to ingest this repo's exact `SKILL.md` format — plus GKE auto-discovery for registering the JARVIS backend/MCP server as agents via A2A Agent Cards. Skills — being small file bundles — no longer need a self-hosted OCI registry or a privileged docker daemon to distribute; they can be published to and fetched from the managed registry directly.

This redoes a previously attempted migration (commit `d73b0a9`, reverted in `d7a763e`) that was backed out only because it landed entangled with an unrelated terminal-bridge rework, not because the plan was wrong. **A full implementation of this exact migration was already built, live-tested, and verified against this same target cluster in a since-abandoned session** (branch `jaar-gcp-registry-migration`, change `openspec/changes/migrate-jaar-to-gcp-agent-registry/` on that branch) — real bugs were found and fixed via live testing (registry `alt=media` download blocked by this project's VPC-SC perimeter, worked around via a GCS-hybrid fetch; `skills.list` never includes `frontmatter`; revision-tracking race in the publish script; uid/gid collision on the cloud-sdk base image). **This change ports that already-verified work forward**, reconciling it against everything `worktree-remote-worker` has gained since that branch diverged (main-brain worker, interactive-PTY terminal rework, the worker infra/ops-tooling change earlier in this session, the worker sidebar, stable session ids) rather than re-deriving the design from scratch.

**Verified before starting this change**: the infra prerequisites from that prior session are still live on the real cluster — GKE Fleet membership (`t2-d-sbx-arch`), the dedicated GCS skills bucket (`d-platform-raytflf9-jarvis-skills`, already containing a published `planner-daily-wrap-up/` skill), and the `agentregistry.viewer` IAM role on the backend/worker Workload Identity service account. Only the **application code** (worker skill-fetch mechanism, backend routes, frontend dashboard card, JAAR removal) needs to be ported.

**One material difference from the prior implementation**: that session switched the worker base image from `docker:dind` to `gcr.io/google.com/cloudsdktool/cloud-sdk:alpine` specifically to get `gcloud`. `gcloud` is now already present on the current `docker:dind` base (added earlier in this session's worker infra/ops-tooling change) — so this change does **not** need to touch the base image at all, avoiding both the base-image debate (settled earlier this session: keep `docker:dind`) and the uid/gid-1000 collision the prior session had to work around.

## What Changes

- **BREAKING**: Remove JAAR entirely — `helm/jaar/` chart, `argocd/jaar-app.yaml` (+ `-local` variant), `secrets/jaar-secret*.yaml`, and all `JAAR_URL` config plumbing. JAAR has no live namespace, ArgoCD Application, or vendored infra-repo config on the target sandbox cluster — this removal has no live-infra teardown component.
- **BREAKING**: Replace the worker's skill-pull mechanism (`worker/entrypoint.sh`: dockerd + `arctl skill pull ... --registry-url $JAAR_URL`) with a `fetch_skill()` shell function that resolves the skill/revision against the Agent Registry API (`gcloud auth print-access-token` + `curl`) and downloads the payload via `gcloud storage cp` from the dedicated GCS bucket (the registry's own `alt=media` download is blocked by this project's VPC-SC perimeter for in-cluster callers — confirmed empirically by the prior session; the registry still owns metadata/discovery, GCS just serves the bytes). Skill-enabled worker pods no longer require `privileged: true` or a docker-in-docker sidecar.
- Remove the `arctl`-based skill install from `worker/Dockerfile` and the dockerd bootstrap from `worker/entrypoint.sh`. `docker:dind` stays as the base image (standing decision from earlier this session) even though nothing in it will actively use dockerd anymore, since the only thing that would justify a base-image change is out of scope here.
- `scripts/publish-skill.sh` + a Makefile target publish `artifacts/skills/*` to the Agent Registry (create/patch skill + revision via the JSON API, upload payload to GCS, poll for `ACTIVE`), replacing the build-Docker-image-and-`arctl register` flow. Run with a human's own `gcloud` credentials (see Non-Goals — no CI Workload Identity Federation).
- Keep the `Worker.skills: list[{name, version}]` JSON shape unchanged — `version` now resolves to a Skill Revision instead of a JAAR OCI tag; no DB migration needed.
- Remove the Agent Registry dashboard card's dependency on JAAR's HTTP API; re-source its skills count from the existing `listSkills()` client call, now backed by a rewritten `GET /api/v1/skills` (Agent Registry-sourced, filtered to skills without a `publisher` field — the project's catalog includes ~64 platform/vendor-published skills alongside JARVIS's own).
- Add the MCP server's `/.well-known/agent-card.json` endpoint and GKE auto-discovery labels/annotations on its Deployment, since the infra prerequisite (Fleet membership) is already satisfied — but per the prior session's live verification, **auto-discovery did not register the MCP server after 1+ hour** with Fleet membership, labels, and a working Agent Card all in place. This change ships the Agent Card endpoint and labels as read/verifiable pieces but does not treat MCP-server-visible-in-registry as a required exit criterion (see Non-Goals).

## Capabilities

### New Capabilities
- `agent-registry-skill-hosting`: Publishing and retrieval of skill files via the GCP Agent Registry Skills API + a dedicated GCS bucket for payload storage, replacing JAAR/arctl-based OCI skill distribution.
- `agent-platform-registration`: A2A Agent Card endpoint and GKE auto-discovery labels/annotations that let the Agent Registry discover the JARVIS MCP server as a registered agent (ships the mechanism; registry-side discovery itself is not a required exit criterion — see prior session's finding).

### Modified Capabilities
- `skill-worker-integration`: skill references stored on `Worker` keep their `{name, version}` shape but resolve against Agent Registry Skill Revisions instead of JAAR name@version OCI refs; worker pod env vars drop `JAAR_URL` and gain `AGENT_REGISTRY_PROJECT`/`AGENT_REGISTRY_LOCATION`; skill-enabled pods no longer run privileged/dind.
- `skill-ci-publishing`: publishing moves from build-Docker-image-and-`arctl register` to `scripts/publish-skill.sh` against the Agent Registry Skills API + GCS, run manually (human `gcloud` credentials) rather than via CI Workload Identity Federation.
- `jaar-artifacts-ci`: artifacts directory structure changes now that JAAR/arctl registration is gone.
- `jaar-dashboard-card`: card's skills count now comes from the backend's Agent-Registry-backed skills endpoint instead of proxying JAAR's HTTP API; MCP Servers/Agents/Prompts counts remain "—" (unchanged limitation, no registry read API confirmed for those).

### Removed Capabilities
- `jaar-deployment`: JAAR is no longer deployed via Helm/ArgoCD anywhere (it already wasn't live on the target cluster; this also removes the local-dev-only chart/Application CR).
- `jaar-gateway-routing`: no HTTPRoute for JAAR since the namespace/service never existed on the target cluster and the local-dev chart is removed.

## Non-Goals (carried forward from the prior session's verified findings — not re-litigated here)

- Getting the MCP server to actually appear in `agentregistry.googleapis.com`'s `mcpServers.list` — Fleet membership, correct labels/annotations, and a working Agent Card were all live for 1+ hour in the prior session without the server appearing. Ships the mechanism; treats registry-side auto-discovery as a known open item, not a blocker.
- CI-driven skill publishing via GitHub Actions Workload Identity Federation — the WIF pool Terraform was written previously and is deliberately not applied (this session already independently hit and resolved the same blocker: the TFE execution identity lacks `iam.workloadIdentityPools.create`, treated as an intentional guardrail rather than something to route around). Publishing stays a manual, human-run step (`make sync-artifacts-skills` / `scripts/publish-skill.sh`) until someone with the right access revisits this.
- Changing the worker base image, Claude Code session/resume logic, or the terminal bridge — unrelated to skill/registry distribution and already settled/shipped earlier in this session.
- Registering `artifacts/agents/` or `artifacts/prompts/` content — both are empty placeholders.
